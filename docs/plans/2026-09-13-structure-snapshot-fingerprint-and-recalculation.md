## 一、目标与设计

修复结构算法已经变化、但同版本活动快照仍被复用的问题，并按当前正式规则重新生成全部启用标的的结构。

- 规则版本升级为 `chan-period-center-hierarchy-cache-fingerprint-v13`，层级算法版本升级为 `center-hierarchy-cache-fingerprint-v13`。
- 保持当前中枢规则不变：低级中枢永久保留，升级通过新增父级 L2/L3 表达，不原地修改 L1。
- 新增稳定的 `calculator_fingerprint`：按固定顺序对 `coverage.py`、`engine.py`、`hierarchy.py`、`models.py`、`period_structure.py`、`rules.py` 和 `knowledge/chan_rules.yaml` 的相对路径及文件内容计算完整 SHA-256。
- 源文件缺失或读取失败时拒绝启动结构计算并输出明确错误，不能退回空指纹继续复用快照。
- 注释、格式或代码内容变化都会改变指纹并触发一次重算，这是本次选择的正确性优先策略。

## 二、实现与接口

- 为 `period_structure_runs` 增加非破坏性字段 `calculator_fingerprint TEXT NOT NULL DEFAULT ''`；历史记录保留，空指纹自然视为过期。
- `PeriodStructureService` 初始化时取得当前指纹，并允许测试注入指纹。快照只有在 `definition_version`、`calculator_fingerprint`、`market_version`、`coverage_version` 全部一致时才能复用。
- `load()` 遇到版本或指纹不匹配时直接走强制重算，不能递归加载旧活动快照。
- 新快照保存当前指纹；`structure_version` 的哈希输入加入规则版本和计算器指纹，使算法来源变化时结构版本也变化。
- `GET /api/health` 和 `GET /api/chart-data/{symbol}` 增加 `calculator_fingerprint` 字段；前端 `ChartData` 将其声明为可选字符串，不改变现有图表行为。
- 将 v12 专用重算、审计脚本改为版本无关的 `scripts/recalculate_structure.py` 和 `scripts/audit_structure.py`，并检查活动版本、当前指纹、层级计数、父子引用和 API 精确级别过滤。
- 更新规则库版本及现有版本断言，但不修改当前缠论计算公式、颜色映射和同级别分解规则。

1. 执行阶段第一步，把本计划块内完整 Markdown 原文逐字写入目标计划文件；若文件已存在则使用 `-2`、`-3` 后缀。立即回读，核验非空、章节完整且实现、API、测试、假设没有丢失；失败时停止后续修改。
2. 保留当前工作区已有的 README、图表布局、样式、启动脚本及未跟踪计划文件，不覆盖或回退这些用户改动。
3. 实现 v13、代码指纹、数据库字段、缓存判定、API 字段及版本无关的运维脚本。
4. 在临时数据库上完成单元和集成测试，不接触生产行情库。
5. 停止并确认不存在本工程 Uvicorn 进程；记录 enabled 股票、活动 run、人工修订和画图对象数量。
6. 使用 SQLite 在线备份能力将主库及已提交 WAL 内容备份到带时间戳的 `data/backups/` 目录；对源库和备份执行 `PRAGMA quick_check`，并核对关键表行数。
7. 先 dry-run 输出执行矩阵，再对执行时所有 enabled 股票的 `5`、`30`、`d`、`w`、`m` 周期、`adjustflag=2` 强制重算。当前预期为 `1A0001`、`1A0688` 共 10 项，但以执行时数据库为准。
8. 每个周期仅在完整写入成功后切换活动 run；任一项失败则整体执行返回失败，不启动服务，并从已验证备份恢复，避免长期保留 v12/v13 混合活动状态。
9. 全部成功后运行数据库审计，启动服务，通过 health、chart-data 和实际页面复核；旧结构 run 不删除，继续保留审计能力。

## 四、测试与验收

- 指纹测试：相同代码和数据复用同一 run；注入不同指纹时，即使行情、覆盖和规则版本相同也必须产生新 run；历史空指纹必须失效；固定输入重复计算得到相同 SHA-256。
- 持久化测试：新字段能迁移旧库、写入和加载；活动 run、结构版本、指纹一致；失败事务不切换活动指针。
- 层级回归测试：把 `1A0001` 目标中枢的 34 笔结构字段固化为独立测试夹具，不依赖本地数据库；验证 1 条进入笔、33 条中枢内笔可拆为 11 个三笔走势，并得到 3 个已确认 L2、1 个 `2/3` L2 候选及 1 个已确认 L3。
- 全量测试：后端基线 `92 passed` 不得回退；前端基线 `50 passed`；生产构建通过。现有 FastAPI 弃用警告和大 chunk 警告记录但不在本次处理。
- 数据库验收：所有执行矩阵项均为 v13、指纹等于当前代码、无缺失父子引用、无跨连续区间消费、中心和走势级别计数与实际记录一致。
- 目标数据验收：
  - 原 L1 `2022-03-16 ~ 2023-11-21` 继续保留，固定核心约为 `[3023.3045, 3290.2561]`。
  - 已确认 L2 分别为 `2022-03-16 ~ 2022-09-13`、`2022-09-13 ~ 2023-02-17`、`2023-02-17 ~ 2023-07-14`。
  - `2023-07-14 ~ 2023-11-21` 为 L2 候选，状态 `provisional`、进度 `2/3`。
  - `2022-03-16 ~ 2023-07-14` 存在已确认 L3。
  - 日线 API 返回 `center_levels=[1,2,3]`、`max_available_center_level=3`；请求 L1/L2/L3 时只返回对应级别，页面可正常切换并显示候选虚线样式。
- 重算前后画图对象数量保持一致；人工结构修订如执行时新增，必须逐条验证目标 ID，失效项进入 conflict，不能静默删除。

## 五、假设与边界

- 使用现有行情数据重算，不在本次同步或修复 BaoStock 数据。
- 分时 `1` 及 `15/60/120/y` 不参与结构重算。
- 不修改中枢升级公式、笔规则、跨周期语义、买卖点或背驰逻辑。
- 数据库迁移只新增字段；旧 v12 run、行情、自选分组和画图数据全部保留。
- 当前服务未运行，但执行时仍按停服、进程核验、备份、重算、审计、启动的完整流程处理。
- 若实现过程中必须实质改变上述算法、数据范围或接口契约，先保存一份新的完整计划版本，再继续修改。
