# 5分钟、30分钟、日线、周线、月线实时刷新方案

## Summary

为 `1分钟、5分钟、30分钟、日线、周线、月线` 建立统一的“缓存数据 + 当前周期临时预览 + 收口后正式确认”机制。

本方案解决四个问题：

- 交易时段内当前周期动态更新；
- 最后一根未完成 K 线不污染正式行情和正式结构；
- 日、周、月收盘后只生成一根逻辑周期 K 线；
- 旧响应、重复拉取、来源变化不会造成覆盖冲突或重复周期记录。

当前已存在的后端 `refresh_period()`、`preview_period()`、日线确认哈希机制继续复用；前端自动刷新范围从当前仅 `"1"` 扩展到 `1/5/30/d/w/m`。

## 1. 周期与数据来源

### 5分钟、30分钟

- 盘中行情来源使用腾讯 `m5`、`m30`。
- 以交易所时间网格生成规范化 `period_key`：
  - `5分钟`：`YYYY-MM-DD HH:MM:00`
  - `30分钟`：`YYYY-MM-DD HH:MM:00`
- 当前未收口周期只保存在内存实时层，返回：
  - `is_forming: true`
  - `status: "provisional"`
- 周期边界后至少 15 秒重新拉取，确认后才写入正式行情并重算正式结构。
- 不能因为数据源返回了未来时间桶就直接展示未来 K 线；适配器必须同时计算 `period_start`、`period_end`，只允许当前有效交易网格进入响应。

### 日线

- 盘中使用腾讯日线响应和最新报价构造当日临时 K 线。
- 当日临时 K 线只进入内存预览，不进入 `confirmed_daily_bars`，不参与正式日线结构和周/月正式投影。
- 日线收口时间固定为交易日 `15:00:15`。
- 收盘后的新请求必须重新获取日线源数据，并通过内容哈希确认后才转为正式日线。

### 周线、月线

周线、月线不再以腾讯返回的不同原始日期作为正式周期主键，避免同一周/月出现多条记录。

- 周线逻辑主键：ISO 周，例如 `2026-W39`。
- 月线逻辑主键：`YYYY-MM`。
- 周/月盘中预览由“已确认日线 + 当日临时日线”聚合：
  - `open`：周期第一交易日日线 `open`
  - `high`：周期内最高日线 `high`
  - `low`：周期内最低日线 `low`
  - `close`：周期最后一条可用日线 `close`
  - `volume`、`amount`：有可靠来源时求和，否则保留缺失状态，不伪造
  - `trade_date`：周期内最后一个交易日
- 周/月正式 K 线只使用已确认日线聚合生成。
- 周/月不再直接依赖腾讯 `week/month` 响应作为正式写入来源；该来源可以保留为诊断或比对来源，但不能绕过日线确认体系写入正式周/月数据。

## 2. 统一状态模型

所有目标周期统一使用以下状态：

- `cached`：只读到历史缓存，没有执行刷新；
- `provisional`：当前周期正在形成，只存在实时预览层；
- `confirmed`：周期已收口，正式行情和正式结构已落库；
- `stale`：刷新失败，保留上一份正式数据并返回错误信息；
- `unavailable`：没有足够有效数据，不生成伪造 K 线。

接口返回继续保留现有字段，并增加统一的 `period_refresh`：

```json
{
  "period_key": "2026-W39",
  "state": "provisional",
  "is_forming": true,
  "server_time": "2026-09-22T10:00:00+08:00",
  "latest_data_at": "2026-09-22",
  "source_revision": "source-revision",
  "request_started_at": "2026-09-22T09:59:50+08:00",
  "last_success_at": "2026-09-22T10:00:00+08:00",
  "next_period_finalize_at": "2026-09-25T15:00:15+08:00",
  "is_today": true,
  "error": null
}
```

兼容现有客户端：

- 保留 `intraday_refresh` 字段；
- 新前端优先读取 `period_refresh`，没有时回退到 `intraday_refresh`；
- 保留 `forming_bar`、`structure_preview`、`structure_persisted` 字段。

## 3. 持久化与冲突控制

### 统一逻辑周期键

为 `market_bars` 增加 `period_key`：

- `1/5/30`：规范化 K 线起始时间；
- `d`：`YYYY-MM-DD`；
- `w`：ISO 周键；
- `m`：自然月键。

将唯一约束从原始 `trade_date` 扩展为：

```text
(symbol, timeframe, adjustflag, period_key)
```

`trade_date` 保留为显示和排序字段，不再承担逻辑周期唯一性。

### 正式确认表

将日线确认能力扩展为通用周期确认表：

```text
period_confirmations(
  symbol,
  timeframe,
  adjustflag,
  period_key,
  row_hash,
  source_revision,
  request_started_at,
  fetched_at,
  confirmed_at,
  PRIMARY KEY(symbol, timeframe, adjustflag, period_key)
)
```

日线现有 `daily_bar_confirmations` 需要迁移到该通用机制，或保留兼容视图。

### 收口规则

- 5分钟/30分钟：周期边界后 15 秒确认；
- 日线：交易日 `15:00:15` 后确认；
- 周线：本 ISO 周最后交易日 `15:00:15` 后确认；
- 月线：本月最后交易日 `15:00:15` 后确认。
- 如果交易日历不完整，不计算周/月最终收口时间，也不提前确认。

### 防止旧响应覆盖

每次刷新记录：

- `request_started_at`
- `fetched_at`
- `source_revision`
- `row_hash`

执行以下限制：

- 请求开始时间早于收口时间的响应，不能直接成为正式确认；
- 旧请求响应不能覆盖较新的成功响应；
- 同一 `period_key` 相同哈希重复提交必须幂等；
- 同一 `period_key` 内容变化时立即删除旧确认，必须重新确认；
- 所有行情写入、确认记录、结构快照切换必须在同一事务边界内完成。

## 4. 后端接口与刷新流程

扩展：

```text
GET /api/chart-data/{symbol}?timeframe=1|5|30|d|w|m&refresh=true
```

规则：

- `refresh=true` 支持 `1/5/30/d/w/m`；
- `refresh=true` 与 `before` 同时出现时返回 `400`；
- 普通请求不访问行情源，只读取缓存和当前内存预览；
- 刷新只处理当前股票和当前图表周期，不刷新整个股票池。

刷新流程：

1. 获取交易日历和当前交易阶段；
2. 获取当前周期源数据；
3. 标准化周期键和周期边界；
4. 将未收口数据放入实时内存层；
5. 将已达到收口条件的数据通过幂等写入正式表；
6. 若正式行情内容发生变化，重算对应周期正式结构；
7. 若仍有形成中数据，生成纯内存结构预览；
8. 返回正式数据、临时数据、刷新状态和错误信息。

周/月刷新必须先确保当日线状态已完成：

1. 刷新日线；
2. 日线盘中只保留临时数据；
3. 收盘后先确认日线；
4. 再由已确认日线聚合周/月；
5. 最后更新周/月正式结构。

## 5. 前端自动刷新

将当前：

```ts
const realtimePeriod = timeframe === "1";
```

改为支持：

```ts
const realtimePeriod = ["1", "5", "30", "d", "w", "m"].includes(timeframe);
```

行为要求：

- 切换周期后先显示缓存，再立即触发一次 `refresh=true`；
- 交易时段每 15 秒刷新；
- 接近周期边界时按照 `next_period_finalize_at` 调度收口请求；
- 午休期间暂停轮询，`13:00` 恢复时立即刷新；
- 收盘后在确认时间执行一次补取，然后停止；
- 页面隐藏时停止请求，重新显示时立即补刷；
- 切换股票或周期时取消旧请求；
- 保留缩放、绘图、副图和未保存绘图状态；
- 实时合并必须按 `period_key`，不能只按 `trade_date`；
- 当前周期显示“形成中”，正式周期显示“已确认”。

## 6. 历史数据迁移

执行前必须：

1. 停止服务；
2. 同时备份 `chant_agent.db`、`chant_agent.db-wal`、`chant_agent.db-shm`；
3. 执行 `PRAGMA quick_check`；
4. 生成重复周期 dry-run 报告；
5. 确认删除集合和保留集合后再执行迁移。

迁移内容：

- 为所有历史行情补写 `period_key`；
- 日线按日期归并；
- 周线按 ISO 周归并；
- 月线按自然月归并；
- 周/月优先使用已确认日线重新聚合；
- 无法由完整日线重建的周期保留一条最新有效记录，并标记为需要重新获取；
- 删除同一逻辑周期的多余记录；
- 重建唯一索引；
- 重新计算 `5/30/d/w/m` 正式结构；
- 核对结构版本、行情版本和计算指纹。

## 7. 测试与验收

### 后端单元测试

覆盖：

- 日、周、月、节假日和跨月周期键；
- 盘中临时数据不写入正式表；
- 5/30 边界后转为正式；
- 日线收盘确认；
- 周线最后交易日确认；
- 月线最后交易日确认；
- 收盘前请求跨越收盘后返回时仍不能直接确认；
- 相同内容重复请求幂等；
- 内容变化使旧确认失效；
- 旧响应不能覆盖新响应；
- 同一周/月多日期输入最终只保留一根逻辑周期 K 线；
- 周/月 OHLCV 聚合结果正确；
- 行情源失败时保留正式数据并返回 `stale`。

### API 测试

覆盖：

- 五个目标周期 `refresh=true`；
- `refresh=true&before=...` 返回 `400`；
- 普通请求不触发网络刷新；
- `period_refresh`、`forming_bar`、`structure_preview` 字段一致；
- 日线失败时周/月不错误地显示为正式可用；
- 收口后正式结构版本发生变化；
- 重复收口请求不产生重复结构运行。

### 前端测试

覆盖：

- `1/5/30/d/w/m` 均启动轮询；
- 周期切换取消旧请求；
- 页面隐藏暂停、重新显示立即刷新；
- 当前周期按 `period_key` 合并；
- 临时 K 线不重置缩放和绘图；
- 正式切换后移除 `provisional` 标记；
- 失败时保留旧图并显示错误状态。

### 验收标准

- 交易时段内当前周期在数据源更新后最多约 15 秒反映到图表；
- 日线、周线、月线都能显示当日、当周、当月形成中 K 线；
- 周/月同一逻辑周期在数据库中始终只有一条记录；
- 收盘后重新拉取不会产生重复 K 线；
- 旧数据源响应不能覆盖新数据；
- 当前预览不污染正式结构、正式确认和日线 L2 投影；
- 服务重启后正式数据、确认状态和结构版本保持一致；
- 保持现有 1 分钟分时刷新行为兼容。

## Assumptions

- 使用 `Asia/Shanghai` 和 A 股交易日历；
- 集合竞价只更新报价，不生成正式日/周/月 K 线；
- 5/30 分钟盘中使用腾讯分钟源；
- 日线收盘确认使用日线正式源；
- 周/月正式 K 线统一由已确认日线聚合；
- 当前数据库中已存在的周/月重复记录属于迁移范围；
- 不连接真实交易账户，不改变 `paper_only` 约束；
- 本计划确认后，第一步先原文保存到上述计划文件并回读核验，再开始任何业务代码修改。
