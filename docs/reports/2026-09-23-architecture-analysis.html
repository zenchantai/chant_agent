04三条贯穿全局的不变式

引擎的骨架。V31 那一代重构基本就是在把这三条写实。

A所有权账本

同级别同连续流的直接单位只能有一个正式拥有者：L1 拥有笔，L2 拥有段证明。entry / departure / retest / connection / boundary_evidence 只能进 context_unit_ids，可以重叠，但不进 owned_unit_ids。

08目录职责

目录职责值得注意的地方
app/后端全部逻辑，19 个模块，无子包引擎（纯函数）与服务（有状态）边界清晰，periods.py 是 period_key 的唯一定义处
knowledge/规则契约：yaml（运行时校验）+ md（人读版）参与计算器指纹——改规则文本即触发全量重算
web/src/React + ECharts 前端，25 个文件types.ts 83 行高密度定义，是接口的实际契约
scripts/4 个运维脚本：审计 / 重算 / 两个迁移全部 dry-run 优先，--execute 前复制 db/wal/shm 三件套
tests/29 个后端测试文件按规则版本命名：test_v31_candidate_ownership、test_z_wave_expansion、test_reference_profile
docs/plans/57 份日期命名方案文档等于一份完整重构编年史（V25→V26→V27→V29→V30→V31）
docs/reports/每次大版本晋级后的验证报告与 plans 配对，形成「方案 → 实现 → 验证」闭环
data/SQLite 库 + 备份 + 导入 CSV不入 Git；backups/ 里有带时间戳的迁移前快照

目录设计上最强的一点：docs/plans/ 与 tests/ 的命名直接绑定规则版本。这条「每次规则变更都留方案 + 验证报告 + 版本化测试」的纪律，是这个项目能在两周内完成 6 次结构引擎重构而不失控的实际原因——而不是某个技术选型。

5 项 我的判断

我的判断 a · 全局锁 + 持锁重算是当前最可能的性能天花板

一次 ensure 触发的 analyze_period_ranges 是 CPU 密集全量重算，持锁期间所有其他请求（含左栏报价、切换股票）被阻塞。

反方：这是单用户本地工作台。_snapshot_cache 已按 run_id 缓存快照，命中时不落库不重算；chart_realtime 的增量设计正是为此，docs/plans/2026-09-23-kline-realtime-performance.md 的存在支持「已知取舍」这个解读。建议先量 Server-Timing（main.py:521 已埋点），再决定是否拆读写连接。
我的判断 b · 启动全表扫描随数据量线性恶化

可改为建好唯一索引后只扫 period_key IS NULL，或用一张 schema_migrations 表记录完成状态。

反方：作者显然知道这是迁移代码——docstring 明写「Filling the key is lossless」，且刻意不做删除。作为一次性迁移它是正确的，缺的只是完成标记。这是我认为最值得修且风险最低的一条。
我的判断 c · 结构 run 需要保留策略，而不是「该删」

代码注释已把回收定义为 explicit maintenance operation，说明是留位而非遗漏。缺的是那个入口：可配置保留窗口 + 手工回收脚本。

我的判断 d · chan_structure.py 2 051 行不等于该拆，App.tsx 2 190 行该拆

前者内聚的是同一套不变式（所有权、前缀稳定、修订链），拆开容易让不变式跨文件漂移——chan_expansion.py 和 chan_direction.py 已经是按「证据种类」切出的合理边界。

相比之下：App.tsx 的拆分收益更明确，因为周边已有 10 个纯函数模块 + 对应测试，说明拆分路径已经验证可行。
我的判断 e · 这套架构最强的部分是可审计性，不是算法

三重指纹 + run 快照 + 修订链 + 证据时间分离 + dry-run 迁移，这套组合让「结构算错了」可定位、可回滚、可复现。对缠论这种规则本身存在解释分歧的领域，这个选择比追求算法先进更正确。
